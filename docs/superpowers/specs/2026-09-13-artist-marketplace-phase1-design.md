# Онлайн-галерея художников — дизайн проекта и Этап 1 (Фундамент: авторизация и роли)

## Обзор продукта

Полноценный маркетплейс, где художники продают уникальные (единственные в
экземпляре) физические картины напрямую покупателям. Язык интерфейса —
русский, валюта — таджикский сомони (TJS). Доставку организует сам
художник (платформа только хранит статус доставки и адрес получателя).
Оплата на сайте — целевая функция продукта, но не приоритет для первых
этапов: в MVP используется заглушка/ручное подтверждение.

Три роли пользователей:
- **Покупатель** — регистрируется свободно, просматривает галерею,
  оформляет заказы.
- **Продавец (художник)** — регистрируется, но получает доступ к
  продаже только после одобрения администратором (анкета проходит
  модерацию). Каждая выставляемая картина тоже проходит модерацию
  админом перед публикацией.
- **Админ** — модерирует заявки продавцов и карточки картин, видит все
  заказы. Аккаунт создаётся вручную (без формы саморегистрации).

## Дорожная карта по этапам

Проект слишком велик для одной спецификации и одного плана реализации,
поэтому разбит на последовательные подпроекты. Каждый получает свою
спецификацию и план перед началом реализации.

1. **Этап 1 — Фундамент (авторизация и роли).** Полная спецификация
   ниже. Регистрация покупателя/продавца, анкета продавца, модерация
   продавцов админом, защищённые разделы, заглушки личных кабинетов.
2. **Этап 2 — Галерея и личный кабинет художника.** CRUD картин
   (фото, описание, цена, размеры, категория), отправка картины на
   модерацию, админ-очередь модерации картин, публичная галерея
   (каталог, поиск/фильтры, страница художника с Telegram-контактом,
   страница картины).
3. **Этап 3 — Заказы и корзина.** Корзина, оформление заказа (адрес
   доставки), статусы заказа (оформлен → упакован → отправлен →
   доставлен), история заказов у покупателя/продавца, обзор заказов у
   админа. Оплата — заглушка (статус "ожидает подтверждения оплаты").
4. **Этап 4 — Реальная оплата.** Интеграция платёжного провайдера,
   подходящего для Таджикистана (требует отдельного исследования —
   международные провайдеры вроде Stripe там не работают напрямую),
   возможно комиссия платформы.
5. **Позже (по желанию, вне текущей дорожной карты).** Чат
   покупатель↔художник, уведомления, отзывы/рейтинги, избранное.

## Этап 1 — Фундамент: авторизация и роли

### Технологический стек

- **Next.js** (App Router) на **Vercel**.
- **Clerk** — управление идентификацией (регистрация, вход, сессии,
  готовые UI-компоненты `<SignIn/>`/`<SignUp/>`). Устанавливается как
  нативная Vercel Marketplace-интеграция.
- **Neon Postgres** (через Vercel Marketplace) с **Drizzle ORM** —
  прикладные данные: пользователи, роли, заявки продавцов.
- **Vercel Blob** — зарезервировано под загрузку фото картин
  (понадобится с Этапа 2, но интеграцию имеет смысл поставить сразу).

Выбор обоснован в ходе брейнсторминга: Clerk снимает необходимость
писать и поддерживать хэширование паролей, восстановление доступа и
защиту от брутфорса самостоятельно; Neon — реляционная БД,
естественно подходящая для сущностей с чёткими связями
(пользователь → заявка → картины → заказы в будущих этапах).

### Модель данных

**`users`** — зеркало личности из Clerk + прикладная роль
| Поле | Тип | Описание |
|---|---|---|
| `id` | uuid, PK | |
| `clerkUserId` | text, unique, not null | Связь с аккаунтом Clerk |
| `email` | text | |
| `fullName` | text | |
| `role` | enum: `buyer` \| `seller` \| `admin` | По умолчанию `buyer` |
| `createdAt` | timestamp | |

**`seller_applications`** — анкета и статус одобрения продавца
| Поле | Тип | Описание |
|---|---|---|
| `id` | uuid, PK | |
| `userId` | uuid, FK → `users.id`, unique | Одна активная анкета на пользователя |
| `displayName` | text | Публичное имя художника/студии |
| `bio` | text | |
| `telegramContact` | text, nullable | Для связи с покупателем (вместо чата в MVP) |
| `status` | enum: `pending` \| `approved` \| `rejected` | |
| `rejectionReason` | text, nullable | |
| `reviewedByAdminId` | uuid, FK → `users.id`, nullable | |
| `submittedAt` | timestamp | |
| `reviewedAt` | timestamp, nullable | |

`users.role` — это то, что реально открывает доступ к разделам сайта.
`seller_applications.status` — отдельно отслеживает жизненный цикл
модерации анкеты. Одобрение админа — одна транзакция: `status →
approved` **и** `users.role → seller` одновременно. При отклонении
`role` остаётся `buyer`; пользователь может отредактировать и заново
отправить ту же анкету (статус возвращается в `pending`).

Админ-аккаунт создаётся вручную (seed-скрипт/прямая запись в БД) —
самостоятельной регистрации админов нет.

### Поток регистрации и одобрения

1. Регистрация через Clerk (`<SignUp/>`). На экране регистрации
   пользователь выбирает: "Я покупатель" или "Хочу продавать картины".
2. Webhook `user.created` от Clerk (`/api/webhooks/clerk`) создаёт
   запись в `users` с `role = buyer`.
3. Если выбран вариант "продавец" — после создания аккаунта редирект
   на `/become-seller`: форма (имя художника, био, Telegram) создаёт
   `seller_applications` со статусом `pending`; показывается экран
   "заявка на рассмотрении".
4. Админ на `/admin/sellers` видит очередь заявок со статусом
   `pending` → одобряет или отклоняет (с указанием причины при
   отказе).
5. Одобрение выполняет транзакцию: `seller_applications.status =
   approved`, `users.role = seller`, синхронно обновляется
   `publicMetadata.role` в Clerk (см. ниже).
6. Отклонение: `status = rejected`, сохраняется `rejectionReason`;
   пользователь видит причину в своём кабинете и может отредактировать
   и повторно отправить анкету.

### Защита маршрутов

Роль хранится в собственной БД (источник истины), но дублируется в
`publicMetadata` Clerk при каждом изменении — чтобы `middleware.ts`
мог проверять роль мгновенно по данным сессии, без похода в БД на
каждый запрос.

| Раздел | Доступ |
|---|---|
| `/`, `/gallery` (заглушка на этом этапе) | Публично |
| `/sign-in`, `/sign-up`, `/become-seller` | Публично / любой авторизованный |
| `/dashboard/buyer/*` | Любой авторизованный пользователь |
| `/dashboard/seller/*` | Только `role = seller`; продавцы со статусом `pending`/`rejected` видят страницу статуса заявки вместо кабинета |
| `/admin/*` | Только `role = admin` |

На этом этапе личные кабинеты — заглушки: у покупателя пустой список
"мои заказы", у продавца пустой список "мои картины" (реальный CRUD —
Этап 2).

### Тестирование

- Несколько сквозных (Playwright) сценариев на ключевые пути:
  регистрация покупателя; регистрация продавца → статус "на
  рассмотрении"; одобрение админом → доступ в кабинет продавца;
  отклонение админом → доступ к повторной подаче анкеты.
- Юнит-тесты на прикладную логику одобрения/смены роли (транзакция
  обновления `users.role` + `seller_applications.status`).

### Вне рамок Этапа 1

Каталог картин, загрузка фото, корзина/заказы, оплата, чат — не
входят в этот этап (см. дорожную карту выше).
